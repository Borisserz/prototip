# 1. Зачем это сравнение и как его читать

Статья Epsilon Metrics описывает **целевую архитектуру** продукта для корпоративной аналитики: пользователь задаёт вопрос на естественном языке, система сама планирует шаги, получает данные, строит графики и готовит материалы для решений.

**prototip** — не копия Epsilon Workspace, а **рабочий прототип той же идеи** на демо-данных. Сравнение нужно, чтобы на совещании честно ответить:

- «Мы движемся в ту же сторону, что и ведущие вендоры?» — **да, по архитектуре агентов и сценарию «вопрос → ответ с графиком»**.
- «Можно ли уже ставить вместо промышленной BI?» — **нет**, не хватает корпоративного слоя данных, поиска по отчётам, масштаба и эксплуатации.

Для одной таблицы это работает; для корпорации — недостаточно. **В сравнении не штрафуем**, но в разделе 3.1 честно фиксируем альтернативу. |
| **3. Слой знаний** | Семантическая модель: метрики, таблицы, связи, SQL-шаблоны | `data/sample.csv` + `ALLOWED_COLUMNS` + промпты с примерами SQL/графиков | 🟡 **25%** | **Без RAG** у Epsilon всё равно остаётся **формализованный слой знаний** (метаданные DWH). ## 2.3. SQL-агент: эволюция из статьи (варианты 1 → 2 → 3)

Статья выделяет три ступени зрелости SQL-решения. Наш `DataAgent` укладывается в **вариант 2–3**.

| Ступень в статье | Описание Epsilon | prototip (`DataAgent`) | Сходство | Логическое пояснение |
|------------------|------------------|------------------------|----------|----------------------|
| **Вариант 1** | LLM только генерирует SQL; пользователь копирует в редактор | ❌ Не наш путь | — | Мы **сразу перешли** к автоматическому выполнению. В прототипе нет сценария «отдали только текст SQL». |
| **Вариант 2** | Генерация + **автовыполнение** в хранилище + возврат таблицы | ✅ DuckDB выполняет `SELECT` по CSV | ✅ **90%** | Поток **идентичен**: промпт → SQL → execute → records. Отличие: у них API к DWH; у нас DuckDB in-memory над `df`. Для демо это **та же архитектурная роль** «SQL Tool». |
| **Вариант 3** | **Агентная логика**: ошибки → анализ → исправление → повтор; динамический поток | ✅ До **3 попыток** self-correction; structured output; whitelist; auto `LIMIT` | 🟡 **70%** | Мы делаем **self-correction при ошибке выполнения** (как в статье), но **не** полный ReAct/Tree-of-Thoughts с произвольным выбором tools. Поток **фиксированный внутри агента**, а не «модель решает всё на лету». Для прототипа — достаточная реализация идеи v3. |
| **Учёт бизнес-правил** | Метрики, определения, JOIN по корпоративной схеме | FEW_SHOT с примерами; правило `period LIKE '2024-%'`; 8 колонок | 🟡 **40%** | Синтаксис SQL модель знает в обоих случаях. **Логические ошибки бизнес-уровня** у них снижаются слоем знаний/RAG; у нас — только промптом. На одной таблице ошибок меньше; на DWH — риск выше. |
| **Безопасность SQL** | Валидация, контроль качества, соответствие политикам | Только `SELECT`, blacklist операций, whitelist колонок, `LIMIT` | 🟡 **60%** | Принцип «не дать модели писать что угодно» — **общий**. У enterprise будет полноценный SQL-governance; у нас — **минимальная песочница** для прототипа. |

**Итог по SQL:** по **механике** (сгенерировал → выполнил → починил при ошибке) prototip **очень близок** к тому, что статья называет зрелым SQL-агентом. По **корпоративному контексту** — сильно проще.

# 3. Подробные логические блоки (простым языком)

## 3.1. Чем мы **заменяем** RAG в прототипе (и почему этого мало для enterprise)

В статье RAG подтягивает фрагменты документации и метаданных **перед** SQL. Если RAG не использовать, у Epsilon всё равно остаётся **слой знаний** (таблицы, метрики, связи).

**У prototip вместо этого три механизма:**

1. **Статическая схема** — список из 8 колонок в промпте (`ALLOWED_COLUMNS`).
2. **FEW_SHOT** — примеры хороших SQL и графиков прямо в промпте.
3. **Schema awareness в Planner** — планировщик подсказывает data_agent реальные имена колонок.

**Логика:** для **одной демо-таблицы** этого хватает, потому что пространство сущностей маленькое. Для **корпорации** не хватает, потому что:

- метрики определены словами («выручка», «активный клиент»), а не только колонками;
- десятки таблиц и JOIN;
- документация меняется, промпт не масштабируется.

**Вывод:** мы **не повторяем RAG**, но и **не повторяем полноценный слой знаний** — только его **упрощённый суррогат**.

---

## 3.2. Почему spec-first графики — это «тот же Charting Agent, но иначе»

Статья: модель пишет Python → выполнить → картинка.  
prototip: модель пишет JSON-спецификацию → `viz/charts.py` → картинка.

**Общая логика (одинаковая):**

1. Есть таблица после SQL.
2. LLM **решает тип визуализации** и смысл осей.
3. Код системы **рисует** график без участия пользователя.

**Разная логика (разные trade-off):**

| | Python от LLM (Epsilon) | ChartSpec (prototip) |
|---|-------------------------|----------------------|
| Гибкость | Высокая | Средняя (12 типов) |
| Безопасность | Ниже (exec) | Выше (нет exec) |
| Единый стиль | Сложнее гарантировать | Гарантирован `viz/style.py` |
| Тестируемость | Сложнее | Проще (pytest на spec + render) |

Для **совещания с руководством** наш путь **логичнее**: все слайды выглядят как из одной BI-системы.

---

## 3.3. Почему Planner — главное доказательство «мы в той же парадигме»

Одна модель в чате (как ChatGPT с SQL) — это **вариант 1–2** из статьи.

**prototip и Epsilon** идут дальше: **отдельный планировщик** решает:

- нужен ли один график или дашборд;
- в каком порядке звать агентов;
- что передать следующему шагу.

Это **буквально** раздел статьи «Иерархическая структура (hierarchical chat)» и диаграмма «Planner → SQL → Chart → Slide Deck».

**Отличие:** у них в плане может быть **поиск отчёта**; у нас план строится вокруг **расчёта из CSV**.

## 3.4. Карта агентов: кто кому соответствует

| Роль в статье Epsilon | Агент в prototip | Комментарий |
|----------------------|------------------|-------------|
| Planner / координатор | `PlannerAgent` | Прямое соответствие |
| SQL-агент | `DataAgent` | Прямое соответствие |
| Charting Agent | `ChartAgent` + `viz/charts.py` | Роль та же, реализация другая |
| Агент аналитических выводов | `AnalystAgent` | Явно выделен у нас |
| Комплексный дашборд | `DashboardAgent` | Близко к «несколько графиков в одном ответе» |
| Slide Deck / презентация | `PresentationAgent` | pptx вместо их slide pipeline |
| Поиск отчётов и дашбордов | — | **Нет** |
| Мессенджер / доставка | — | **Нет** |
| Tool-агенты (API) | FastAPI частично | Только pull API, не push в Slack |

# 5. Формулировки для совещания

### Одно предложение

**prototip — это локальный прототип той же мультиагентной логики, что Epsilon Metrics описывает для диалогового BI: планировщик, SQL-агент, агент графиков и агент выводов, но на демо-данных и без корпоративного слоя знаний, поиска отчётов и интеграций.**

### Три тезиса «за»

1. **Та же пользовательская ценность:** вопрос → цифры → график → выводы (и опционально презентация).
2. **Та же архитектура:** иерархический planner и специализированные агенты, а не «один чат на всё».
3. **Безопаснее визуализация для демо:** spec-first вместо выполнения кода от нейросети.

### Три тезиса «честно против» (почему это прототип, а не Workspace)

1. **Один CSV** вместо DWH и семантической модели компании.
2. **Нет поиска** по существующим отчётам — только пересчёт.
3. **Нет production-контура:** доставка в каналы, governance, масштаб, SLA.

### Если спросят «насколько похоже в процентах»

> «По **идее и архитектуре агентов** — примерно **70–80%**. По **готовности заменить корпоративную платформу** — **не сопоставимо**: это демонстрационный референс, а не Epsilon Workspace.»
